# 任务系统增强 — 复建需求规格（行为需求版）

> 目的：在目标程序上重建以下功能。本文只定义**要什么**（用户可见行为、业务规则、验收标准），不约束具体技术实现——后端实现方式由复建者自行设计。
> 适用于任何"任务 + 目标"型系统。文中的「任务状态」请映射到目标程序自己的任务状态机。

---

## 1. 任务执行方式（创建时三选）

### 需求

创建任务时，用户必须三选一：

1. **立即执行**（默认）：创建后任务立即进入执行流程。
2. **暂不执行**：仅创建任务记录，任务停留在「未启动」状态；不占用并发额度；用户随时可手动启动。
3. **定时执行**：用户指定一个未来时间点；**由服务端**在该时间自动启动任务（前端不做倒计时逻辑）。

### 业务规则

- R1 执行计划必须**持久化**：服务进程重启后，未到期的计划必须继续生效、到点照常启动。
- R2 到点启动必须是**服务端行为**，且必须**幂等**：同一计划绝不因服务重启、多次轮询而启动两次。
- R3 到点时若任务依赖（如 LLM）不可用：**不得**启动任务、**不得**清除计划——计划保留，依赖恢复后自动启动。（启动后卡死比不入队更糟）
- R4 手动启动：未启动任务可随时手动启动；若存在计划，启动时计划自动取消（提前执行语义）。
- R5 任务一旦启动（无论到点或手动），执行计划即视为已消费。
- R6 计划时间必须晚于当前时刻；否则拒绝并给出明确提示。

### 接口行为要求

- 创建接口必须接受执行方式与计划时间参数。
- 必须提供「设置/修改/取消计划」的能力（仅未启动任务可操作）。
- 必须提供「手动启动」能力（仅未启动任务可操作）。
- 任务列表/详情数据必须包含：执行方式状态、计划时间（未排程为空）。

### 验收标准

1. 创建定时任务（2 分钟后）→ 任务为未启动态，列表可见计划时间 → 到点后 1 个轮询周期内自动变为运行中，计划时间清空。
2. 重启服务进程 → 计划仍在 → 到点仍自动启动。
3. 未启动任务手动启动 → 立即运行、计划清除。
4. 依赖（LLM）不可用时到点 → 任务保持未启动、计划保留；依赖恢复后自动启动。
5. 同一计划尝试两次启动 → 只成功一次。

## 2. 任务编辑

### 需求

创建后可修改任务的**定义字段**：名称、描述、目标、分类、任务超时、心跳间隔、资产覆盖度开关、关联来源任务、LLM 配置链、执行计划。

- R0 **LLM 配置链**：编辑表单包含 LLM 配置链编辑（有序列表，第一项为当前生效配置）。保存时若链发生变化必须持久化，并**立即对运行中的任务生效**（后续模型调用使用新链）。
- R1 **描述 / 目标 / 关联来源任务**：仅「未启动」与「已结束（终态）」任务可修改。

### 业务规则（状态边界——核心）

- R1 **描述 / 目标 / 关联来源任务**：仅「未启动」与「已结束（终态）」任务可修改。
  原因：运行中任务的执行上下文已随首轮规划固化；修改任务级字段不影响进行中的执行，只会造成认知不一致。运行中调整目标应走「目标管理」（显式触发重新规划）。
- R2 **名称 / 分类 / 超时 / 心跳 / 覆盖度开关**：任意状态可修改。
- R3 **执行计划**：仅未启动任务可修改（设置/改期/取消）。
- R4 **关联企业范围不可编辑**：创建时确定（企业关联牵动资产归属同步，替换风险大）——编辑界面只读展示并说明原因。
- R5 部分更新语义：只更新请求中明确提供的字段；未提供的字段保持原值。
- R6 编辑必须**立即对后续所有流程生效**（保存后打开编辑应看到新值；运行规划读到新值）——不允许只写存储不更新运行态。
- R7 校验：名称/描述/目标非空；分类必须存在；计划时间晚于当前；超时≥0；心跳有下限。
- R8 修改失败必须返回明确的字段级原因（尤其是状态冲突时，提示用户正确的替代操作路径）。

### 接口行为要求

- 必须提供部分更新接口：一次请求可只改一个字段，也可组合改多个。
- 编辑成功必须返回编辑后的完整任务数据。
- 状态不允许时返回明确的业务错误（含建议操作），不是泛化的失败。

### 验收标准

1. 未启动任务编辑全部字段 → 保存 → 重新打开编辑/详情，各字段均为新值。
2. 运行中任务：修改描述/目标 → 被拒绝且提示原因；修改名称 → 成功。
3. 已结束任务：修改描述 → 成功。
4. 计划：未启动任务设置计划 → 列表显示；取消计划 → 清空；改期 → 更新。
5. 保存后服务进程重启 → 新值仍在（持久化验证）。

## 3. 重新进行（重跑）

### 需求

已结束（完成/失败/超时）的任务可「重新进行」：任务恢复运行，在**保留**全部历史产出（事实/资产/图谱）的前提下，围绕原目标重新规划并执行。

### 业务规则

- R1 **核心语义**：重跑前必须把所有「已达成」的目标重置为「未达成」。否则规划器会立即再次判定"目标已全部达成"而秒退——用户看到的"重新进行"等于什么都没做。这是本需求最重要的一条。
- R2 历史产出不得清除：它们是新轮次的参考与对照。
- R3 非终态任务不可重跑：未启动任务用「启动」；运行中任务无需重跑。拒绝时必须说明。
- R4 失败/超时的任务重跑时，其失败/超时状态产生的限制（如超时时钟）必须一并解除。
- R5 并发已满时，重跑的任务进入等待队列，有空位自动开始。
- R6 重跑后必须有可见反馈：状态变化 + 规划活动出现（用户能确认"真的在跑"）。

### 接口行为要求

- 必须提供「重跑」操作；非终态调用时返回明确业务错误。
- 重跑成功返回任务当前状态（运行中或排队中）。

### 验收标准

1. 已完成任务重跑 → 状态变为运行中/排队中；**目标状态从已达成变为未达成**。
2. 重跑后规划器产生**新的规划轮活动**（不是立即再次结束）——这是回归重点。
3. 未启动任务调用重跑 → 明确拒绝。
4. 历史事实/资产在重跑后仍存在。

## 4. 前端：任务表单抽屉（创建/编辑共用）

### 需求

1. 新建与编辑使用**同一个表单组件**（右侧抽屉形态），字段/布局/校验完全同构；编辑模式打开时预填当前值（每次打开都重新预填，非仅首次）。
2. 表单输入状态隔离在表单组件内部——输入时页面其他区域不得发生重渲染卡顿。
3. 编辑模式的差异化：
   - 隐藏创建专属区块：任务模板、测绘搜资产、文件上传、「首个意图」直投、任务级拦截规则编辑（提示到详情页管理）。
   - **状态锁**：任务运行中/已暂停时，描述/目标/关联任务输入禁用，并显示原因与替代操作路径。
   - 关联企业：编辑模式只读展示（含不可编辑的原因）。
   - 执行方式：仅未启动任务可修改。
4. 数据自加载：抽屉打开时自行加载下拉所需数据（分类/企业/任务列表/LLM 配置），不依赖调用方传入。
5. 提交成功：关闭抽屉、刷新列表、按任务状态给出差异化提示（如"可点 ▶ 启动"、"可点 ⟳ 重新进行"）。
6. 所有失败必须有明确 toast 提示。

### 验收标准

1. 新建：三选执行方式逐一切换，界面随选随变；定时未填时间提交被阻止。
2. 编辑：每次打开预填正确；保存后列表与详情即时反映新值；再打开确认持久化。
3. 运行中任务打开编辑：描述/目标灰显 + 原因说明。
4. 输入长文本时页面无卡顿（state 隔离验证）。

## 5. 列表/详情：按状态变化的操作按钮

### 需求（按钮状态矩阵）

| 任务状态 | 列表行内 | 详情页 |
|---|---|---|
| 未启动 | 编辑 + ▶ 启动 | ✏️ 编辑 |
| 运行中 | ⏸ 暂停 | ⏸ 暂停 |
| 已暂停 | ▶ 继续 | ▶ 恢复 |
| 已结束 | ▶ 重新进行 | ⟳ 重新进行 + ✏️ 编辑 |
| 排队中 | 显示排队态 | — |

- R1 按钮占位宽度恒定：状态切换时**替换**按钮而非增删，避免列宽跳动。
- R2 未启动且带执行计划的任务：状态徽章下方显示「MM-dd HH:mm 自动启动」。
- R3 每次操作必须有成功/失败 toast；失败后刷新数据让按钮回到正确形态。

### 验收：逐状态核对按钮矩阵；带计划的任务显示计划时间小字；终态 ▶ 可点且触发重跑。

## 6. 流量页重构

### 6.1 请求可编辑与重放

1. 详情区的原始请求报文（HTTP 原文）可编辑；编辑后标记「已修改」+ 提供「还原」按钮恢复原文。
2. 重放：把（编辑后的）报文按原目标重新发送——需从报文还原目标主机；不跟随重定向；重放流量**不计入**流量记录（无痕）。
3. 支持对已捕获记录一键重放（无编辑）。
4. 重放结果**替换**详情区的响应展示，并提供「原始响应 / 重放响应」切换。
5. 报文无法解析/目标不可达 → 明确错误提示，页面不崩。

### 6.2 布局

6. 详情区 Request 与 Response **左右双栏**（窄屏退化为上下）。
7. 点击列表行，详情面板**内联展开在表格下方**（非弹窗）。
8. 列表区与详情区之间有**可拖拽分隔条**，调整高度并记忆。
9. URL 展示合并进重放操作行（紧凑，去掉独立 host 行）。
10. 筛选：常用筛选一行紧凑展示；**高级筛选默认折叠**；存在生效的高级筛选条件时保持展开；清空后恢复折叠。

### 验收标准

1. 编辑请求参数 → 重放 → 新响应展示，可切换原始/重放对比。
2. 「还原」后请求恢复原文、修改标记消失。
3. 重放不可达主机 → 明确错误，页面不崩；重放流量不出现在流量列表。
4. 拖拽高度即时生效；筛选折叠行为符合上述规则。

## 7. 多标签导航（keep-alive）

### 需求

1. 左侧菜单的每个功能页以**标签页**打开；重复点击同一页面不重复开签，而是激活已有签。
2. **切换标签不销毁组件**（隐藏而非卸载）：滚动位置、未提交的表单内容、定时器在切回后保持原状。
3. 每个标签可独立关闭（×）；关闭当前签自动跳到相邻签；全部关闭回默认页。
4. 标签条位于页面 header 第一行（与版本号/用户区同一栏）。
5. 满幅详情类页面（如任务详情）不进标签系统，保持全屏独立路由。

### 验收标准

1. 打开 ≥3 个标签逐个切换，各页滚动位置与未提交表单内容保持。
2. 关闭当前签自动跳相邻；重复点击菜单无重复标签。

## 8. 系统设置子菜单

### 需求

1. 系统设置拆为两个子页：「界面设置」（UI 偏好集合，原侧边栏偏好弹层迁入）+「系统配置」（运行时开关，如并发上限、LLM 配置入口）。
2. 原侧边栏偏好入口移除，无残留死链。
3. **并发上限修改后必须确认保存成功**——保存后界面回读实际值（曾出现"界面改了 3、实际仍是 1"的事故）。
4. 子页切换不丢各自未提交的表单内容。

### 验收标准

1. 两子页独立切换互不干扰、内容保留。
2. 并发上限保存 → 界面回读新值 → 底层配置查询确认落库。
3. 侧边栏无残留入口。

## 9. 漏洞详情页「提交到补天」入口（触发提交技能）

### 需求

1. 漏洞详情页头部提供「提交到补天」按钮；点击弹确认框（可填目标厂商 cid，可选）。
2. 确认后行为：**创建一个独立的 AI 对话会话**，自动发送一条结构化指令（含漏洞编号、名称、cid、以及合规提醒），并跳转到该会话页面。
3. 会话中的 AI agent 按既定提交技能（SKILL：拉取漏洞材料 → 核对厂商归属 → 起草报告 → 自动填表）执行。
4. **合规硬约束**：指令中必须明确"最终提交按钮由用户人工点击"；agent 只起草与填表。填写公告弹窗等表单前置步骤可程序化完成，但最终提交动作永远人工。
5. 继承漏洞只读（inherited）时按钮不显示。
6. 会话标题自动命名为「提交漏洞 #编号」，便于回溯。

### 验收标准

1. 点按钮 → 弹确认框 → 确认 → 自动创建会话并跳转，会话中出现结构化提交指令。
2. 指令包含漏洞编号/名称/可选 cid，且包含人工确认提醒。
3. 继承漏洞详情页无此按钮。

## 10. 界面布局：全局菜单栏的任务视图切换

### 需求

1. 任务页的「当前任务 / 已归档」切换控件**上移到全局菜单栏**（与版本号/用户区同一栏），不再放在任务页内部。
2. 切换状态为**全局共享**：在菜单栏切换后，任务页本体与归档页同步响应（状态存储独立于页面组件，页面只消费）。
3. 任务页本体只读该状态，不持有副本——避免两处状态漂移。

### 验收标准

1. 菜单栏切换「已归档」→ 任务列表页自动切到归档视图；切回同理。
2. 从其他标签页切回任务页，视图与菜单栏选择保持一致。
